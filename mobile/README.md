# Еда — Android-дневник питания

Версия 1.0.17+18, Android 8.0 и новее. [Установка и обновление](https://food-consumption.solovyshka.com/app/).
Резервный вход: https://vladislavsolovei.ru/food-consumption/app/.

В «Настройки» можно выбрать автоматический режим, русский сервер,
французский сервер (OVH) либо свой адрес. Явный выбор использует только указанный
сервер, включая проверку и скачивание обновлений; автоматический сохраняет переключение
при недоступности. Выбор сохраняется после перезапуска. При переключении между двумя
публичными серверами уже подключённого приложения код повторно не нужен.
Старые настройки сохраняют прежний автоматический режим.

Можно написать или продиктовать, что съедено, добавить фотографию, сохранить запись
в очередь либо сразу нажать «Разобрать и рассчитать». Голос распознаётся на коробке
через GigaAM с резервным Whisper. Текст после распознавания можно исправить.
Кнопка «Разобрать очередь» передаёт до 30 записей в один запуск существующего Grok Bot.

Результат сохраняется автоматически, даже если телефон закрыт. В дневнике и результате
разбора продукты отображаются строками в несколько уровней без горизонтальной прокрутки:
название и кнопки изменения/удаления справа, ниже порция, ккал на 100 г/мл и ккал итог.
БЖУ идут отдельной строкой в формате «Б/Ж/У ≈ 4/3/2 г». Длинные названия переносятся,
при увеличении системного шрифта показатели перестраиваются в одну или две колонки.
В итогах дня рядом с калориями отображаются общие белки, жиры и углеводы.
Сервер суммирует БЖУ из всех активных ручных и разобранных записей выбранного дня,
округляя итог один раз до 0,1 г. При неполных данных показывается предупреждение;
полностью неизвестный итог — прочерк. Оценочные итоги отмечены ≈.
БЖУ отображаются в граммах на съеденную порцию, в порядке белки / жиры / углеводы.
Grok возвращает значения на 100 г/мл, сервер вычисляет итог через Decimal с округлением
до 0,1 г. Неизвестные значения — прочерк, подтверждённый ноль — 0.
Исходное количество и единица, даты, приёмы пищи, источники и пояснения сохраняются
в базе и ответах API, но не выводятся в таблице. Кнопка тестового запроса Grok убрана.

Типовые значения и расчёты по фотографии — оценки. Жирность молока сама по себе
не задаёт точную калорийность конкретной марки. Подтверждённые значения с этикетки
повторно используются для совпадающего названия и единицы. Неизвестная масса или
калорийность остаётся пустой и не входит в итог; дневник показывает число таких позиций.
Продукты можно добавить вручную, исправить после разбора или удалить.
В ручном вводе и изменении продукта доступны белки, жиры и углеводы в граммах
на 100 г/мл. Поля необязательны: пустое значение неизвестно, явный ноль сохраняется.
Значения пересчитываются на порцию и входят в итог дня. Изменение только порции
сохраняет прежний источник БЖУ; исправленные БЖУ используют выбранный источник.

Фото выбирается системным диалогом без общего доступа к галерее. Создаётся уменьшенная
JPEG-копия до 1600 пикселей без EXIF, исходник не меняется. Черновик хранится на телефоне;
при отправке фото сохраняется в PostgreSQL на коробке. Для Grok создаётся временная копия фото на OVH: случайная HTTPS-ссылка под основным
доменом, без входа и списка изображений, доступна 2 часа. После срока она не открывается;
файлы удаляются таймером каждую минуту. Исходное фото остаётся в очереди на коробке для
повторного разбора. Для исходных текстов и возврата результата выдаётся доступ только
к выбранной задаче на один час. Общий токен приложения Grok не получает.
После подтверждённого сохранения записи копия из черновика телефона удаляется.

Очередь, запрос разбора и результат защищены от повторов. UUID и неизменяемые данные
отправки сохраняются в черновике до запроса к серверу. Потеря ответа вебхука не запускает
вторую задачу автоматически. После часа без результата исходные записи освобождаются
для повторного разбора. Ошибки модели возвращают записи в очередь.

## Расход и разница за день

В настройках «Вес и расход в покое» сохраняются имя, дата рождения, пол, вес и рост.
Возраст вычисляется на выбранный день. Прежние параметры владельца сохраняются;
новый пользователь заполняет собственный профиль.
Расход в покое по формуле Миффлина — Сан Жеора:
`10 × вес (кг) + 6.25 × рост (см) − 5 × возраст + 5` для мужчин;
для женщин вместо `+5` используется `−161`.
Это оценка за полные сутки. Бытовая активность и термический эффект пищи отдельно
не учитываются; коэффициент активности не применяется.

В дневнике вводятся только дополнительные калории тренировок за выбранный день.
Без тренировок нужно явно ввести 0; незаполненное значение остаётся неизвестным.
Итоговый расход = покой + тренировки; дельта = съедено − итоговый расход.
При неполном разборе еды дельта помечается как неполная.

Вес и рост сохраняются с текущей даты (Europe/Moscow), последующие дни используют
последние известные значения. Новый вес не меняет прошлые дни. Для дат до первого
сохранения профиля расход в покое неизвестен. В пределах одного дня изменение
веса обновляет запись этого дня. Исходные значения владельца: 96 кг, 170 см.
Старые записи общего расхода сохранены как общий расход и не складываются с покоем;
новый ввод тренировок заменяет такую запись только для выбранной даты.

API: `GET/PUT /energy/profile`, `PUT /days/{YYYY-MM-DD}/activity`
с обязательным nullable `training_kcal` (null очищает запись), префикс `/api/mobile`.
Старый `/days/{YYYY-MM-DD}/energy` сохраняет прежний смысл для совместимости.
Миграция `0011_resting_energy` добавляет таблицу `mobile_energy_profiles` и поле
`training_kcal`; данные еды и старые расходы не изменяются.

## Продукты и рецепты

«Добавить продукт» открывает вкладки «Продукты / Рецепты / Вручную». Начальный
локальный JSON-справочник содержит 164 продукта (около 80 КБ), короткие русские
названия, синонимы и Ккал/БЖУ на 100 г. Поиск учитывает ё/е, десятичную запятую,
часть названия и небольшие опечатки; совпавшая часть названия подсвечивается.
Крупы и гарниры только готовые, варёные на воде без масла; все порции — в граммах.
Значения справочные и отмечены ≈. Промежуточная жирность молока — интерполяция,
а не данные этикетки конкретной марки.

Источник — [USDA SR Legacy](https://fdc.nal.usda.gov/download-datasets/);
ID исходного продукта, английское описание, ссылка и способ оценки остаются в JSON.
Повторное создание: `python deploy/import-food-catalog.py /path/to/FoodData_Central_sr_legacy_food_csv_2018-04.zip`.
Версия справочника независима от APK. После фоновой синхронизации приложение
загружает более новую версию с собственного публичного сервера, проверяет данные
и сохраняет её локально. Поиск не отправляет запросы на каждый символ.

Свои продукты можно создать, изменить и удалить. Для сохранения в справочник
нужны все четыре значения на 100 г; нулевой нутриент вводится как 0. Разовый ручной
ввод по-прежнему допускает неизвестные значения и граммы/миллилитры.

Рецепт хранит снимки ингредиентов, их массы и вес блюда после приготовления.
Сервер считает суммы и значения на 100 г через Decimal; выбирая рецепт, вводят
только съеденную порцию. Ингредиенты взвешивают в том же виде, для которого заданы
значения: сухую крупу вводят вручную или сохраняют как свой продукт. Рецепт
никогда автоматически не изменяет прошлые записи дневника.

Личный справочник хранится в схеме пользователя на коробке и в отдельном
зашифрованном файле телефона. Последняя копия доступна без сети; создание и
изменение сохранённых продуктов/рецептов требует сервера. Черновик рецепта
сохраняется локально, включая UUID запроса; потеря ответа не создаёт дубликат.
Старый ответ фонового обновления не затирает только что сохранённый продукт.
Копии разных аккаунтов и произвольных серверов не смешиваются.

API: `GET /catalog`, `GET /library`, `PUT/DELETE /library/{UUID}` с префиксом
`/api/mobile`. Запись и удаление идемпотентны по request_id; revision защищает
от сохранения устаревшей редакции. Миграция `0013_food_library` добавляет личный
справочник и nullable ссылку на его редакцию в ручной записи. При обновлении
применяется ко всем зарегистрированным схемам пользователей и public.

## Штрихкоды

«Добавить по штрихкоду»: встроенный ZXing без Google Play Services, камера или
ручной ввод GTIN-8/12/13/14. UPC-E сканер преобразует в UPC-A. Контрольная цифра
проверяется сервером; магазинные и весовые коды не поддерживаются. Один код
обозначает вид фабричного товара, а не отдельную упаковку.

Поиск сначала в личном каталоге, затем в Open Food Facts (без платного API).
Источник и лицензия ODbL показаны для данных каталога. Внешние значения требуют
проверки по упаковке. Пустые КБЖУ остаются неизвестными, нули сохраняются.
Ручные значения и фото этикетки можно привязать к коду; «Значения сверены с
упаковкой» отмечает подтверждённые данные. Порция вводится отдельно.

Grok читает таблицу на фото через временную ссылку OVH. Чтение этикетки не
добавляет еду в дневник. Задача и её черновик сохраняются, повтор запроса с тем
же UUID не запускает второй разбор. Каталог сохраняется перед добавлением
продукта в черновик; запись о потреблении создаёт только «Сохранить в дневник».

Миграция `0009_barcode_catalog`: `mobile_barcode_products`,
`mobile_barcode_label_jobs`, nullable `mobile_entry_details.barcode`.
API: `GET/PUT /barcodes/products/{gtin}`, `POST /barcodes/labels`,
`GET /barcodes/labels/{uuid}`. Grok получает авторизацию только своей задачи,
`GET .../input` и `POST .../result`; общий ключ приложения не передаётся.

## Сервер и Grok

Сервис `food-mobile-api`, PostgreSQL на коробке. Новая миграция
`0007_grok_food_analysis` добавляет фотографии, задачи разбора и отдельные таблицы
`mobile_parsed_foods` / `mobile_parsed_nutrition`. Старые записи остаются в
`consumption_entries`. Исходные тексты находятся в `consumption_transcripts`.
Миграция `0008_food_macros` добавляет `protein_per_100g`, `fat_per_100g`,
`carbs_per_100g`, `macros_source` в `mobile_parsed_nutrition` и `mobile_entry_details`.
Для старых записей БЖУ остаётся неизвестным: миграция не запускает повторный разбор.
При изменении порции БЖУ пересчитываются; при смене продукта или единицы старые
БЖУ сбрасываются, если новые значения не переданы явно. Оценочные БЖУ не используются
как подтверждённые данные с этикетки, даже если калорийность известна точно.

Текущий разбор использует существующий вебхук Grok Bot, а не xAI API.
Ключи `GROK_BOT_WEBHOOK_URL` и `GROK_BOT_WEBHOOK_KEY` находятся в закрытом
серверном окружении. Прокси: `GROK_BOT_PROXY_URL` (по умолчанию `http://127.0.0.1:10809`).
`FOOD_GROK_CALLBACK_BASE_URL` задаёт публичный HTTPS-вход (по умолчанию основной домен).
Короткий вебхук передаёт адреса задачи; подробная инструкция и схема результата
читаются отдельным GET, чтобы Grok не обрезал тело запроса. Инструкция находится
в `app/services/grok_analysis.py`. Старый `/preview` оставлен для совместимости.

API: `POST /images`, `POST/GET /queue`, `DELETE /queue/{id}`, `POST /queue/parse`,
`GET /queue/jobs/{uuid}`, `GET /diary`, `PATCH/DELETE /grok/foods/{id}`;
префикс `/api/mobile`. Запуск не равен завершению: приложение проверяет статус задачи.
Grok получает отдельные `input_url`, `result_url` и авторизацию одной задачи.
Результат проверяется по схеме, сохраняется транзакцией, итоги считаются на сервере.
Возврат того же результата повторно не добавляет строки и не перезаписывает ручные правки.

Настройки и черновик телефона зашифрованы Android Keystore, резервное копирование
отключено. Подключение требует персональный код; публичные входы работают через HTTPS.

## Сборка на коробке

Исходники: `/home/solovyshka/builds/food_checking/mobile`.
Flutter: `/home/solovyshka/develop/flutter/bin/flutter`.
Постоянный ключ: `/home/solovyshka/.config/food_checking/android-release.jks`,
параметры — `android-release.properties` там же; `android/key.properties` ссылается на них.
Секреты не входят в репозиторий. Этот ключ необходим для обновления установленного APK.

```sh
cd /home/solovyshka/builds/food_checking
python3 deploy/build-apk.py --skip-publish
# После проверок опубликовать уже собранный файл:
python3 deploy/build-apk.py --skip-build
```

Скрипт проверяет приложение, собирает подписанный APK и выпускает одинаковую версию
на обоих публичных входах. Обновление внутри приложения поддерживает докачку,
проверку размера, SHA-256, пакета и подписи. Микрофон и установку обновления
нужно дополнительно проверить на физическом Android-телефоне.

[Инфраструктура публикации](../deploy/public/README.md).

Пересчёт прошлых дней по запросу владельца использует вес 96 кг и рост 170 см.
Записи расхода `source=rest_only` означают, что дельта считается только по покою:
данные тренировок остаются неизвестными (`training_kcal=null`), ноль не подставляется.
`GET /diary` возвращает `energy_mode=rest_only`, `training_kcal_missing=true` и ≈.
Ввод тренировок через приложение заменяет такую запись обычным расчётом.

## Несколько пользователей

На каждом телефоне вводится свой код подключения. Сервер определяет аккаунт по
ключу доступа и выбирает отдельную PostgreSQL-схему через `schema_translate_map`.
Еда, тексты, фотографии, очереди, Grok, расходы, параметры тела и личный каталог
штрихкодов полностью независимы; основной дневник остаётся в `public`.
Старый код подключения и ключ основного пользователя продолжают работать.
В дневнике показывается имя пользователя, его можно изменить в профиле.
Новый пользователь не получает копию личных параметров владельца.
При смене аккаунта приложение требует сначала сохранить/очистить черновик.

Миграция `0012_mobile_users` добавляет `mobile_person` и владельца callback-задач.
Новые дневники создаются на сервере:
`sudo /opt/food_checking/venv/bin/python /opt/food_checking/deploy/create-mobile-user.py --name 'Имя'`.
Ключ и код хранятся только в приватном `mobile-accounts.json`, заданном
`FOOD_MOBILE_ACCOUNTS_FILE`. Конфигурация обновляется атомарно. Доступ к чужим
схемам нельзя выбрать параметром обычного API-запроса. Callback Grok имеет
собственный доступ к одной задаче, URL содержит серверный параметр `account`.

При будущих обновлениях миграции выполняются для основного дневника и каждой
зарегистрированной схемы: `alembic -x schema=food_user_<uuid_hex> upgrade head`.
Схема нового дневника создаётся полной цепочкой миграций, включая индексы.

На экране разбора Grok показывается только текущая очередь: ожидающие записи
и записи, которые сейчас обрабатываются. Для последних доступна кнопка
«Проверить разбор». История завершённых и неудачных задач в приложении не
показывается; исходные данные и результаты продолжают храниться в базе.
