# План: учёт продуктов через Telegram-бот (фаза 1)

## Цель фазы 1

Только **запись наличия продуктов** голосом. Учёт потребления (еда) — отдельная фаза 2, схема БД заложит это заранее.

**Пример сценария:**

1. Вы отправляете голосовое: «Есть 2 кг картофеля, литр молока и пачка яиц»
2. Бот скачивает аудио и отправляет на сервер
3. Сервер транскрибирует → извлекает структуру → сохраняет в БД
4. В Telegram приходит таблица для проверки; кнопки «Подтвердить» / «Отменить»

## Рекомендуемый стек

| Компонент | Выбор | Почему |
| --- | --- | --- |
| Язык | Python 3.11+ | Экосистема для ботов, STT, API |
| БД | Уже установлен PostgreSQL 16 на сервере | Не ставим второй Postgres; новая БД `food_checking` |
| Деплой | venv + systemd на `brynn` | Docker нет; рядом уже trading/dailybot/Ollama |

| Парсинг | Локальный Qwen через уже стоящий Ollama (`qwen2.5:7b-instruct-q4_K_M`) | `keep_alive=0` после парсинга |

## Архитектура

Всё на `161.104.53.72` (`brynn`, Ubuntu 24.04). Не Docker: Postgres и Ollama уже стоят. Whisper и приложение — отдельные systemd-сервисы. Облачные API не используем.

**Не держать Whisper и Qwen 7B в RAM одновременно** — на 8 ГБ не влезают. Обработка последовательная: сначала STT, потом парсинг.

---

## Схема базы данных (PostgreSQL)

**products** — справочник продуктов: `id`, `name`, `name_normalized`

**inventory_entries** — записи о наличии: продукт, количество, единица, `status` (pending/confirmed/cancelled), `source`, `transcript`, `telegram_message_id`, `recorded_at`, `entry_date`, `created_at`, `confirmed_at`

**consumption_entries** — заготовка для фазы 2 (те же поля даты)
